# Сущность «Задача» в демо (объект в состоянии)

Документ описывает **только объект задачи** в демо-приложении:

- из каких полей он состоит;
- какие смыслы несёт;
- как появляется в данных;
- **как в данных задаётся «предмет задачи»** (оборудование и помещения) — простым языком, не только имена полей в коде.

Связка **модалка создания → payload → объект задачи** — в **`../modal_to_task_mapping.md`**.

---

## Правило для сидов и ИИ: дефолтные задачи не шире ручного создания

**Обязательное правило:** в **`demoDefaultState.js`**, **`demoStateChecklistSeed.js`** и любых других сидах демо **нельзя** подставлять в задачи поля, ключи `config` или сценарные данные, которых **нет** в форме **ручного создания задачи** (модалка создания + секция «Суть задачи» `ChecklistTaskFieldsSection`, см. **`../modal new task.md`** / **`../modal_to_task_mapping.md`**).

Конкретно:

- **`taskFieldDefinitions[].config` для `temperature`** — только то, что пользователь реально вводит в модалке: **`minC`**, **`maxC`**. Не добавлять в сиды **`showCamera`**, произвольные **`label`**, прочие ключи «от себя»; после **`normalizeTaskFieldDefinitions`** в объекте задачи появится то же, что и при сохранении ручной задачи.
- **Корректирующие действия** — как у только что созданной задачи: пустой список, пока пользователь не заполнит блок исключений в модалке (не наполнять сид длинными готовыми списками «для красоты»).
- **Замеры `measurements`** — без заранее вбитых значений °C и без «демо-problem», если это не отдельный согласованный сценарий; по умолчанию слоты как у несделанной задачи: **`—`**, **`pending`**.
- Исключения из этого правила допустимы **только** если явно зафиксированы в документации продукта как отдельный демо-сценарий (не по умолчанию для агента).

Нарушение этого правила приводит к расхождению демо-данных с тем, что пользователь может воспроизвести через UI, и к ложным багрепортам.

## 1. Где хранится

- Задачи лежат в **`demoState.checklistsByNiche`**.

- Ключи ниш: `coffee`, `bakery`, `meat`.

- Значение по ключу — **массив задач**.

- У каждой задачи есть поле **`niche`**  
  (та же строка, что ключ списка) —  
  для фильтров, AI и отображения.

---

## 2. Как объект собирается в коде

- Единая сборка модели: **`buildTaskFromPayload`**.

- Файл:  
  `resources/js/features/demo/domain/checklistTaskModel.js`

- Вызовы:

  - из сидов — **`buildDefaultTask`**;
  - из пользовательского сценария — **`buildChecklistTaskFromPayload`**  
    в `resources/js/features/demo/composables/demoChecklistCustomTask.js`.

- После первичной сборки на чек-листы могут накладываться:

  - **`normalizeAllChecklistTaskMeasurementStatuses`**  
    — статусы слотов и AI-поля задачи (`normalizeTaskAiFields`);

  - **`seedChecklistsTemperatureAi`**  
    — для задач с полем **temperature**  
    и строк замера с разборимым значением **`… °C`**:  
    заполняются **`measurements[].aiWarning`**,  
    уточняется **`task.aiContext`**.

- Файл сидера:  
  `resources/js/features/demo/ai/temperature/seedChecklistsTemperatureAi.js`

- Вызывается при:

  - создании дефолтного state;
  - загрузке из `localStorage`.

Источник «правды» по именам и типам полей:

- код **`buildTaskFromPayload`**;
- типичный объект в консоли после сборки.

## 3. Поля задачи (кратко по назначению)

- **`id`**  
  Уникальный идентификатор в рамках демо.

- **`niche`**  
  Ниша чек-листа: `coffee` / `bakery` / `meat`.

- **`title`**  
  Название задачи.

- **`status`**  
  **Агрегат по задаче**: `boolean` («в норме» / нет).  
  Не путать со статусом отдельного слота в **`measurements`**.

- **`isCustom`**  
  `true`, если задача создана пользователем, иначе из сида.

- **`taskScopeType`**  
  Охват: `equipment` / `rooms` / `standalone`.

- **`equipmentTargetIds`**  
  См. раздел **«Предмет задачи»** ниже — что именно выбрано из оборудования.

- **`roomTargetIds`**  
  См. раздел **«Предмет задачи»** ниже — что именно выбрано из помещений.

- **`scope`**  
  Маркер `standalone` только для типа охвата standalone.

- **`assignedStaffId`**  
  Id ответственного или `null`.

- **`allowAssigneeReportCorrections`**  
  Флаг демо-политики правок отчёта ответственным.

- **`frequency`**  
  Код частоты (в дефолтах часто `custom`).

- **`startDate`**  
  Timestamp начала (мс).

- **`activeWeekdays`**  
  Активные дни недели (`mon` … `sun`).

- **`repeatTimes`**  
  Времена слотов в сутках, строки `HH:mm`.  
  Длина согласована с числом слотов.

- **`taskFieldDefinitions`**  
  Массив определений поля «Суть задачи».  
  В демо в сценарии создания из модалки фактически **один** элемент.  
  Типы: `temperature`, `single_choice`, `ticket`  
  (ветка **timer** в панели выполнения — отдельная эвристика UI, не отдельный пункт этого списка в форме создания).

- **`measurements`**  
  Массив слотов замера по расписанию  
  (подробности — раздел 4 ниже).

- **`correctiveActions`**  
  Список строк — варианты при отклонении  
  (сиды или форма).

- **`aiContext`**  
  Объект контекста AI для **температурных** задач.  
  У нетемпературных обычно отсутствует или обнуляется нормализацией.

Подробные формулировки «что это / зачем» с привязкой к модалке —  
в **`modal_to_task_mapping.md`**.  
При расхождении с кодом приоритет у **кода**.

## 3a. Предмет задачи: оборудование и помещения

Это про то, **к чему привязана задача** в смысле «где на производстве её выполняют»: к конкретным единицам оборудования или к помещениям.

### Оборудование

- Когда тип охвата задачи — **оборудование**, при создании (или в дефолтных данных) задаётся **список выбранных позиций** из раздела конструктора «Предмет задачи».

  - Примеры того, что можно отметить: плита, холодильник, ростер, склад и т.п.

- В сохранённой задаче это хранится не как длинные подписи.

  - В поле **`equipmentTargetIds`** лежат **внутренние короткие коды** — по одному на каждую отмеченную позицию.

- **Понятные названия для людей** («Холодильник 1», «Комбинированная печь») в объекте задачи **отдельно не копируются**.

  - Их подставляют из **общего справочника оборудования** по кодам, когда нужно показать карточку или строку «используется для …».

- Если смотришь задачу в отладчике, смотри **`equipmentTargetIds`** — это и есть выбор оборудования.

  - Какой код чему соответствует по подписи — в конфигурации групп оборудования для задач в репозитории.

### Помещения

- Когда охват — **помещения**, аналогично действует поле **`roomTargetIds`**: коды выбранных зон (производственный зал, камера и т.д.).

- Названия помещений для экрана также подставляются из справочника по кодам.

### Связь с температурой и AI

- **Где стоят датчики / что обслуживаем** (список оборудования или помещений) и **какой режим заложен в AI для температуры** (например хранение или обжарка у кофе) — **разные оси смысла**.

- Режим для расчёта подсказок живёт в **`aiContext`** и правилах контекста AI.

- Список оборудования говорит: **к каким объектам на площадке относится эта задача**.  
  Он **не всегда сам** переключает режим AI на «обжарку» или «охлаждение» — если в данных явно не согласованы выбор оборудования и контекст.

- Поэтому название задачи («Охлаждение зерна») и фактический список кодов оборудования в сиде **могут расходиться** с точки зрения сценария: это ограничение демо-данных, а не «вторая тайная форма» хранения предмета задачи.

## 4. Слот замера: `measurements[]`

Каждый элемент — одна строка расписания на день.

- **`time`**  
  Время слота, `HH:mm`.

- **`value`**  
  Отображаемое значение, например:

  - `-19 °C`, `34 °C`;
  - `28 мин`;
  - текст ответа;
  - `Выполнен` / `Не выполнен`;
  - маркер **`—`** для несделанного слота.

- **`status`**  
  **`success`** | **`problem`** | **`pending`** — состояние **этого слота**.

- **`aiWarning`**  
  Результат AI для температуры: объект для UI или **`null`**  
  (нет числа в строке, pending, нет температурного поля).

- **`correctiveAction`**  
  Выбранная строка из **`correctiveActions`**  
  при фиксации действия на `problem`  
  (иначе `null`).

- **`comment`**  
  Комментарий исполнителя там, где сценарий его задаёт  
  (например `single_choice` / `ticket`).

Статусы слотов при сохранении state нормализуются к этому множеству  
(legacy приводятся к **`pending`**).

## 5. Температура и AI (сущность данных)

### 5.1 `task.aiContext` (только температурные задачи)

Задаётся при сборке через **`buildTaskAiContext`**.

Далее может обновляться:

- при сохранении замера из панели выполнения;
- при **`seedChecklistsTemperatureAi`**.

Типичные ключи:

- **`engine`**  
  например `"temperature-v1"`.

- **`niche`**  
  ниша задачи для профиля.

- **`mode`**  
  режим профиля  
  (`storage`, `proofing`, `chilled`, `freezer` и т.д.)  
  — по правилам в `taskTemperatureAiContext.js` и сохранённому контексту.

- **`taskType`**  
  `"temperature"`.

- **`ccpMin`**, **`ccpMax`**, **`ccpLabel`**  
  границы и подпись CCP.

- **`updatedAt`**  
  ISO-время последнего обновления блока  
  (сидирование AI, ✓ в панели).

### 5.2 `measurement.aiWarning`

Пишется:

- при **✓** в панели выполнения для температуры (`applyPendingMeasurementFromKeypadOk.js`):  
  - **`success`** → **`getHaccpInRangeDisplay`** (только **мясо**; иначе **`aiWarning`** не создаём);  
  - **`problem`** → **`getHaccpWarning`**.

- при обогащении сидов / загрузке из storage — **`seedChecklistsTemperatureAi`**, та же логика по **`status`** строки замера.

**`ai_status` в демо (поле `measurement.aiWarning`):**

- **`null`** — нет данных для AI, **`pending`**, или **успех не мяса** (зелёный блок AI не пишем).

- **`ok`** — **мясо**, замер в CCP; тексты из **`meatStorageThreatBands`**.

- **`warning`** / **`problem`** — отклонение CCP; порог **`problem`** по **`risk`** — **`AI_STATUS_PROBLEM_MIN_RISK_PERCENT`** в **`TemperatureAiAnalyzer`**.

В объекте: заголовок, строки значения/отклонения или «в норме», профильные поля — см. shape в конфиге.

## 7. Сборка задач по умолчанию

Источник списка и полей — **`createDefaultState`** в демо: для каждой ниши задачи проходят **`buildDefaultTask`**, затем на чек-листы назначаются ответственные по умолчанию (**`applyDefaultAssigneesToChecklists`**), после чего для температурных задач вызывается **`seedChecklistsTemperatureAi`**  
(статусы слотов с разобранным значением **°C** приводятся к допуску, заполняется **AI** там, где применимо).

Ниже — что именно попадает в **`demoState.checklistsByNiche`** при «чистом» старте демо: по категориям ниш, с суточным расписанием и сутью задачи.  
Идентификаторы задач (**`coffee-1`**, **`bakery-3`** и т.д.) — внутренние ключи демо; пользователю показываются **названия** и данные карточек.

### Кофейня (`coffee`)

- **Заявка по помещению кофейни** (`coffee-1`)
  - Охват: **помещения** — производственный зал, сырьевой склад, зона приёмки.
  - Суть задачи: **заявка (ticket)** — осмотреть зону, при необходимости фото и файл, кратко описать проблемы в комментарии.
  - Расписание: **два слота** — 09:00 и 15:00; значения не заполнены (**ожидание**).
  - Корректирующие действия: три варианта «служебных» отмазок/причин невыполнения (формулировки из сида).
  - Агрегат **`status` задачи** в дефолте: **выполнена** (как задано в базовой заготовке).

- **Охлаждение зерна** (`coffee-2`)
  - Охват: **оборудование**.

  - В дефолте привязан **кулер зерна** (код **`eq-coffee-bean-cooler`**).  
    По нему движок AI выставляет режим **охлаждения** и подтягивает тексты из справочника полос кофе для этого процесса.

  - Суть задачи: **температура** — как в модалке создания: подпись поля **`Температура`**, допуск **15…25 °C** (целевое окно после обжарки); смысл «охлаждение зерна» — в **названии задачи**, не в отдельной кастомной подписи поля. Камера в форме — **`showCamera`**.

  - Расписание: **четыре слота** — 00:00, 06:00, 12:00, 18:00.

  - Заполнен только **первый** слот (**00:00**): **34 °C** — выше верхней границы допуска, статус слота **отклонение**, AI подсказка по полосе охлаждения; слоты **06:00 / 12:00 / 18:00** — **не сделаны** (**ожидание**).
  - Набор корректирующих действий: от погрешности измерения до выброса продукции (несколько строк).
  - Агрегат задачи: **не в норме** (есть невыполненные/проблемные слоты).
  - Эта же задача — цель демо-сценария «зерно» (тосты, диплинк, панель выполнения); логика сценария завязана на **первый слот со статусом ожидания** в списке.

- **Проверка маркировки и упаковки партии** (`coffee-3`)
  - Охват: **оборудование** — транспортный контейнер и сухой склад.
  - Суть задачи: **один вопрос с выбором** — корректны ли упаковка и маркировка (да / нет, есть замечания).
  - Расписание: **два слота** — 09:00 и 15:00; не заполнены.
  - Корректирующие действия: проверка маркировки, карантин партии, фото и менеджер.
  - Агрегат задачи: **не в норме**.

- **Заявка в техслужбу по кофемашине** (`coffee-4`)
  - Охват: **оборудование** — кофемашина.
  - Суть задачи: **заявка** — оформить обращение при нестабильной работе кофемашины.
  - Расписание: **два слота** — 10:00 и 16:00; не заполнены.
  - Корректирующие действия: уточнение заявки, резервное оборудование, эскалация в техслужбу.
  - Агрегат задачи: **не в норме**.

### Пекарня (`bakery`)

- **Охлаждение помещения** (`bakery-3`)
  - Охват: **помещения** — производственный зал и холодильная камера.
  - Суть задачи: **температура помещения**, допуск **16…22 °C** (как в поле CCP).
  - Расписание: **четыре слота** — 00:00, 08:00, 12:00, 16:00.
  - В демо-сидах в ячейках заданы **длительности в минутах** (28 / 34 / 30 мин и пустой слот) — это не градусы; парсер температуры их не превращает в °C, AI по температуре для таких строк **не строится** из значения «мин». Статусы слотов в сиде: успех / отклонение / успех / ожидание (как задано для демо-картинки).
  - Корректирующие действия: оборудование, дверь, контрольный замер и др.
  - Агрегат задачи: **не в норме**.

- **Заявка по помещениям пекарни** (`bakery-4`)
  - Охват: **помещения** — производственный зал и сырьевой склад.
  - Суть задачи: **заявка** — вентиляция и влажность в выбранных помещениях.
  - Расписание: **два слота** — 09:00 и 15:00; не заполнены.
  - Корректирующие действия: заявка в техслужбу, приоритет и фото, эскалация менеджеру.
  - Агрегат задачи: **не в норме**.

- **Сроки сырья** (`bakery-5`)
  - Охват: **помещения** — сырьевой склад и зона приёмки.
  - Суть задачи: **один вопрос с выбором** — актуальны ли сроки сырья и маркировка.
  - **Расписания слотов замеров нет** (массив **`measurements`** не задаётся в дефолтной заготовке).
  - Агрегат задачи: **в норме**.

### Мясо (`meat`)

- **Морозильная камера** (`meat-1`)
  - Охват: **оборудование** — морозильник и холодильное хранилище.
  - Суть задачи: **температура**, допуск **−21…−17 °C**.
  - Расписание: **четыре слота** — 00:00, 06:00, 12:00, 18:00.
  - Значения в сиде: **−19 °C** и **−17 °C** (в норме), **−5 °C** (вне нормы), последний слот пустой (**ожидание**).
  - Корректирующие действия: дверь, поломка, выключение, возврат продукции, утилизация.
  - Агрегат задачи: **не в норме**.

- **Маркировка партии** (`meat-2`)
  - Охват: **помещения** — склад готовой продукции и офис ОТК.
  - Суть задачи: **один вопрос с выбором** — корректна ли маркировка партии.
  - **Расписания слотов нет.**
  - Агрегат задачи: **в норме**.

- **Температура хранения** (`meat-3`)
  - Охват: **оборудование** — два холодильника.
  - Суть задачи: **температура**, допуск **0…4 °C**.
  - Расписание: **четыре слота** — те же углы суток, что у морозильной камеры.
  - Значения: **2,1 °C** и **2,3 °C** (в норме), **5,6 °C** (вне нормы), последний слот пустой.
  - Корректирующие действия: расширенный список (дверь, погрешность, поломка и т.д.).
  - Агрегат задачи: **не в норме**.

- **Заявка по оборудованию термоконтроля** (`meat-4`)
  - Охват: **оборудование** — зонд и холодильник.
  - Суть задачи: **заявка** — обслуживание оборудования термоконтроля.
  - Расписание: **два слота** — 10:00 и 16:00; не заполнены.
  - Корректирующие действия: ремонт/калибровка, резерв, контроль срока.
  - Агрегат задачи: **не в норме**.

- **Санобработка** (`meat-5`)
  - Охват: **помещения** — мойка и производственный зал.
  - Суть задачи: **заявка** — доработка санобработки.
  - **Расписания слотов нет.**
  - Агрегат задачи: **в норме**.

### Общее для всех дефолтных задач

- Частота в модели: **`custom`**, активные дни недели — **пн…пт** (как в константах сборки).
- Дата старта задачи при создании state — **начало текущих суток** (по утилите даты демо).
- **`repeatTimes`** выводятся из расписания **`measurements`** (времена слотов), если слоты заданы.
- Ответственные на карточках — из **демо-персонала** (назначение по умолчанию, не часть ручного ввода пользователя).
