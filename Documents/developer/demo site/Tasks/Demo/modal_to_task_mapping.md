# Сопоставление: модалка «Новая задача» → объект задачи (демо)

Этот документ — **карта поведения**: какие поля есть у задачи, что они означают, откуда берутся (модалка / сид / модель), и как связаны между собой. **Код тут не описываем**, только смысл и правила.

---

## 1) Жизненный цикл данных (в двух словах)

### 1.1 Черновик формы (UI модалки)

Внутри формы пользователь редактирует «черновик» (draft). В нём есть UI-поля, которые **не обязаны существовать в задаче** (например, `scheduleSlotCount`).

### 1.2 Payload на создание задачи (что «улетает» из формы)

При создании из черновика собирается payload. Он содержит только данные, которые имеют смысл хранить/обрабатывать как часть бизнес-объекта.

### 1.3 Объект задачи (то, что хранится в состоянии демо)

Модель строит «целевую задачу» из payload (и/или из сида по умолчанию). На этом этапе модель:

- добавляет системные поля (`id`, `isCustom`, и т.п.)
- приводит типы/форматы
- **всегда** делает `measurements` массивом слотов

---

## 2) Что именно уходит из модалки в payload (без деталей реализации)

Из модалки в payload попадают поля:

- `title`
- `taskScopeType`
- `assignedStaffId`
- `frequency`
- `startDate`
- `repeatTimes`
- `activeWeekdays`
- `equipmentTargetIds`
- `roomTargetIds`
- `taskFieldDefinitions`
- `allowAssigneeReportCorrections`
- `correctiveActions` (список «Ответов исключений», если заполнен)

**Важно:**

- `repeatsPerDay` **не хранится**. Кол-во повторов в сутки определяется длиной `repeatTimes` и количеством слотов в `measurements`.
- `scheduleSlotCount` — **UI-поле** для удобного ввода (сколько слотов/повторов). В задачу напрямую не записывается.
- legacy: если в старом сохранении встречается `repeatsPerDay`, он влияет только на нормализацию черновика (чтобы не потерять число слотов), но в задаче поля не будет.

## 3) Поля объекта задачи (все свойства + что это и зачем)

Ниже перечислены **свойства задачи**, которые ты видишь в консоли у дефолтных и созданных задач (пример как в твоём сообщении).

### 3.1 Идентичность и происхождение

- **`id: string`**
  - **что это**: уникальный идентификатор задачи.
  - **зачем**: ключ для удаления/поиска/рендера списков и связывания UI с конкретной задачей.
  - **откуда**: у дефолтных — из сида или fallback; у пользовательских — `custom-${niche}-${uuid}`.

- **`isCustom: boolean`**
  - **что это**: признак происхождения задачи.
  - **зачем**: UI/логика может отличать «пользователь создал» vs «зашито по умолчанию».
  - **откуда**: модель выставляет по источнику (`default`/`custom`).

### 3.2 Смысл задачи

- **`title: string`**
  - **что это**: название задачи (то, что пользователь вводит).
  - **зачем**: основной «смысловой заголовок» и главное описание того, что делать.
  - **откуда**: модалка.

### 3.3 Охват (предмет задачи)

- **`taskScopeType: \"equipment\" | \"rooms\" | \"standalone\"`**
  - **что это**: тип охвата — по оборудованию, по помещениям или «процесс/компания».
  - **зачем**: включает/выключает блок «Предмет задачи» и определяет, какие поля целей допустимы.
  - **откуда**: модалка/сид → нормализация.

- **`equipmentTargetIds?: string[]`**
  - **что это**: список выбранных единиц оборудования.
  - **зачем**: «куда именно» относится задача (например, конкретные холодильники).
  - **когда есть**: только если `taskScopeType === \"equipment\"`.

- **`roomTargetIds?: string[]`**
  - **что это**: список выбранных помещений.
  - **зачем**: «куда именно» относится задача (например, моечная/склад/кухня).
  - **когда есть**: только если `taskScopeType === \"rooms\"`.

- **`scope?: \"standalone\"`**
  - **что это**: дополнительный маркер для standalone-задач.
  - **зачем**: проще отличать standalone в UI/логике без повторных проверок.
  - **когда есть**: только если `taskScopeType === \"standalone\"`.

### 3.4 Ответственный и правила корректировок

- **`assignedStaffId: string | null`**
  - **что это**: id назначенного сотрудника (или `null`).
  - **зачем**: фильтрация/отображение «кому назначено», в демо — влияет на таблицы/бейджи.
  - **откуда**: модалка (или автоподстановка в дефолтах).

- **`allowAssigneeReportCorrections: boolean`**
  - **что это**: разрешено ли ответственному «подправлять» отчёт.
  - **зачем**: демонстрация контроля доступа/процесса согласования (в демо без реальных прав).
  - **откуда**: модалка/дефолт.

### 3.5 Расписание (когда выполнять)

- **`frequency: string`**
  - **что это**: код частоты выполнения (в демо часто `\"custom\"`).
  - **зачем**: управляет режимами расписания (ежедневно/раз в неделю/кастом и т.п.).
  - **откуда**: модалка/сид.

- **`startDate: number | null`**
  - **что это**: timestamp даты старта (миллисекунды).
  - **зачем**: точка отсчёта расписания/показа актуальных слотов.
  - **откуда**: модалка/сид.

- **`activeWeekdays: string[]`**
  - **что это**: активные дни недели (`mon..sun`).
  - **зачем**: когда задача «должна» выполняться.
  - **откуда**: модалка/дефолт (обычно Пн–Пт).

- **`repeatTimes: string[]`**
  - **что это**: список времени слотов в формате `HH:mm`.
  - **зачем**: задаёт «сколько раз в день» и «в какие моменты» ожидаются замеры/выполнение.
  - **связь**: длина `repeatTimes` = число слотов в дне (и обычно совпадает с `measurements.length`).
  - **откуда**: модалка (или выводится из `measurements` для пресетных многослотовых задач).

### 3.6 Статусы (важно не путать два уровня)

- **`status: boolean`** (статус *задачи*, агрегат)
  - **что это**: агрегат «в норме/не в норме» на уровне задачи.
  - **зачем**: быстрые списки/дашборды/пилюли статуса по задаче.
  - **как интерпретировать**:
    - `true` — «в норме» (ok по агрегату)
    - `false` — «не в норме» или «есть мониторинг по слотам» (в демо часто так обозначают составные/многослотовые кейсы)
  - **важно**: отображаемый ключ для UI (`ok|repeat|problem`) вычисляется отдельно (по boolean и «многослотовости»).

- **`measurements: Array<MeasurementSlot>`** (статусы *слотов*)
  - **что это**: список слотов замеров/фиксаций по расписанию.
  - **зачем**: показать «что и когда» должно быть измерено/зафиксировано.
  - **важно**: это **всегда массив** после сборки задачи (и для дефолтных, и для custom).

### 3.7 Конструктор «Суть задачи»

- **`taskFieldDefinitions: Array<TaskFieldDefinition>`**
  - **что это**: описание выбранного «типа поля» в секции «Суть задачи» (температура/дата/таймер/и т.п.) и его конфиг.
  - **зачем**: задаёт, какие данные пользователь должен фиксировать при выполнении.
  - **особенность текущего UX**: в демо сейчас разрешено **только 1 поле**.

### 3.8 «Ответы исключений» (что писать при провале)

- **`correctiveActions?: string[]`**
  - **что это**: список заранее заготовленных пояснений/вариантов действия «если задача провалена».
  - **зачем**: чтобы при `problem` пользователь быстро выбрал причину/действие из списка.
  - **когда есть**:
    - у «составных/пресетных» задач — обычно есть (может быть и пустым массивом, если так задано);
    - у custom — появляется, если пользователь реально заполнил список в модалке.

---

## 4) Контракт слота замера (`measurements[]`)

Каждый элемент `measurements` имеет вид:

- `time: string` — время слота `HH:mm`
- `value: string` — отображаемое значение/ожидание (в демо — человекочитаемый текст)
- `status: \"success\" | \"problem\" | \"pending\"`
  - `success` — слот выполнен/в норме
  - `problem` — отклонение
  - `pending` — ещё не зафиксировано

**Важно:** в таблицах UI сейчас показывается *буквально* значение `status` слота.

---

## 5) Как читать примеры (из консоли)

### 5.1 Дефолтная «составная» задача (пример как `coffee-2`)

Характерные признаки:

- `isCustom: false`
- `measurements.length > 1` (несколько слотов в день)
- обычно есть `correctiveActions` (список заранее)
- `repeatTimes` согласованы со слотами `measurements`

Пример shape (укорочено):

- `id: \"coffee-2\"`
- `title: \"Охлаждение зерна\"`
- `taskScopeType: \"equipment\"`
- `equipmentTargetIds: [\"eq-cold-storage\", \"eq-fridge-1\", ...]`
- `repeatTimes: [\"00:00\", \"06:00\", \"12:00\", ...]`
- `measurements: [{time, value, status}, ...]`
- `correctiveActions: [\"...\", \"...\", ...]`

### 5.2 Пользовательская задача из модалки (пример как `custom-coffee-...`)

Характерные признаки:

- `isCustom: true`
- `id` начинается с `custom-...`
- `taskFieldDefinitions` содержит 1 элемент (выбранный тип поля)
- `correctiveActions` есть только если заполнены «Ответы исключений»
- `measurements` строятся по `repeatTimes` и для новых custom слоты обычно `pending`

Пример shape (укорочено):

- `id: \"custom-coffee-...\"`
- `title: \"Температура камер\"`
- `taskScopeType: \"equipment\"`
- `equipmentTargetIds: [\"eq-stove\", \"eq-fryer\", ...]`
- `taskFieldDefinitions: [{...}]`
- `repeatTimes: [\"00:00\", \"06:00\", \"12:00\", ...]`
- `measurements: [{time, value, status:\"pending\"}, ...]`
- `correctiveActions: [\"ф1\", \"ф2\"]` (если заполнено)
